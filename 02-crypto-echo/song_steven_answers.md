TCP is needed for this assignment because it maintains a stateful and reliable connection that preserves encryption session context between the client and server Once the TCP connection is established, both of the endpoints can then safely assume that every byte sent is delivered in order without any missing pieces. This reliability is especially important when the client and server are sharing secret infromation for encryption. Both sides must stay in sync, and TCP makes sure no messages are lost or mixed up while they are talking. If we used UDP instead, every message would be sent on its own with no guarantee that it even reaches the reciever. UDP is connectionless and stateless, meaning each datagram is independent. Using UDP would force the application to reimplement sequencing, retansmission, and acknowledgement at the appliation layer. There is also no notion of persistent sessions so the server has no guarentee messages come from the same client or correspond to the same key, greatly complicating the design. TCP's stateful nature means that it keeps track of the whole conversation. Meaning, once keys are exchanged, they remain valid until the connection closes. It allows both client and server to trust the information used to protect the data stays consistent during communication. Without TCP, secure and sycched encrypted communiation would be unreliable and far more complex to manage.

2.  The protocol in this assignment uses a structured message format with header and payload instead of sending raw text . This design make the communication between client and server more organized, predictable, and just overall easier to process. The header contains information such as message type, directions, and payload length, which lets the reciever know exactly what kind of data to expect and how much of it to read. Without this, the reciever would not know where one message ends and the next beigins. Using binary PDU structure also makes the protocol more reliable and flexible. The same format can handle both plantext messages and encrypted bytes without needing to change how messages are parsed. It also makes it easier to add new features later, For ex. like digital signitures, without redesigning the whole system. If we had only sent plain text, the server would need to manually search for seporators or keywords, which can easily break if teh data contains any special characters. With PDU, each message is self-contained and clearly defined, allowing server and client to process data consistently.

3.  Even though TCP reliably delivers data, it is a stream oriented protocol. This means that TCP treats all transmitted bytes as one continuous flow rather than seperate nessages. When a program calls recv(), it might recieve only part of a message or multiple messages combined in one call. TCP ensures that bytes arrive in order, but it does not indicate where one message ends and the next begins. This is why the payload_len field is so important. It tells the reciever exactly how many bytes belong to the current messages payload. This lets the program know how much data to read before completing the message. Without the payload_len field, the reciever would have no way to tell if a recv() call returned a full message, a partial, or multiple. If we removed the field and just relied on TCP, the reciever might mininterprt data, read too much or too little, or wait forever for bytes that don't come. The payload_len value establoishes a clear message boundary inside the continuous TCP stream, making it possioble to parse multiple PDUs correctly.

4.  The key exchange happens before any encrypted messages are sent because both client and server need to agree on a set of keys that are shared and unique to that connection. We don't use pre shared hardcoded keys because that makes the system unsafe. If someone were to get the key once, they can decrypt all messages between client and server forever. By generating new keys for each session, every connection has its own encryption setup, meaning even if one session's key was leaked, it would not affect future or past communications. Creating new keys per connection also prevents attacks. Each session has its own state, so it remembers which key pair was exchanged and uses it only when the TCP connection is alive. If the conenction were to drop, the client and server would lose that session state and the keys are thrown away. When the client reconnects, a new key exchange happens ensuring the keys are never reused. This design depends on TCP because it TCP maintains a continuous, stateful connection.Since UDP does not have sessions, it would not be able to keep track of which key belongs to which commuication.

5.  Even though the client and server already know their roles, the directions field is still included because it makes the prorcol more clear, safer, and easier to debug. It acts as a built in label that tells the reciever whether the message is meant to be a request or a response. THis helps confirm that both client and server are behaving correctly. For ex. if the server were to accidentally send a message marked as a request instead of reponse, it can be detected imeediately. The direction field also makes the protocol more self-documenting and reliable. When reviewing logs or debugging, you can immediately see what type of message was sent, which makes tracking and troubleshooting much easier. In addition, this design helps future proof the system. If the protocol is ever extended beyond simple client server communication, the direction field already provides the flexibility needed to handle that. Overall, it adds clarity, validation, and scalability to the communication process.
